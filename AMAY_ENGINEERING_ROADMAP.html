Closing the gap between what VisPruner cuts and what a request actually feels

VisPruner removes most of LLaVA's visual tokens and cuts prefill compute by 56–60%, measured directly. That win barely survives contact with the rest of the system. This roadmap turns the profiling phase's findings into a sequenced, benchmark-gated engineering plan — one measurable change at a time.

Read literally, not proportionally — these three bars measure different quantities, not one shrinking number. Raw isolated-latency gain measured 15.2%; 13.4% is a derived estimate correcting a timer that excluded ~86.7ms of image preprocessing (never re-measured directly). The 3.8% capacity figure is provisional: its two load sweeps were not temporally interleaved. The 58% prefill figure never moves — it is the one number in this chain that doesn't degrade under any condition tested.
What did profiling find?

Five measurements that define this roadmap

Every phase below traces back to one of these. Full detail and source files live in AMAY_VISPRUNER_PROFILING_REPORT.md.

56–57

The diversity loop runs backwards

Iterations of VisPruner's own token-selection loop at 128 tokens — predicted from the code, confirmed in the raw trace. At 576 tokens (unpruned), it runs zero iterations. Pruning harder currently makes selection more expensive, not less.

ab_trace_vtn128_isolated.json · llava_arch.py:160–176
6–8%

Decode barely moves

vs. a 56–60% prefill reduction. Decode reads the full weight matrix every step regardless of visual-token count, and it's 6–16× larger than prefill — the single biggest reason the algorithmic win doesn't reach the user.

ab_noload_comparison_table.txt
1 req

The server is strictly serial

Verified from source, not inferred: csnbs/server.py's handler calls generate() synchronously with no yield point. One request in flight, ever — capacity is capped by mean service time regardless of how cheap a single request gets.

csnbs/server.py · _infer_model
crash

Concurrency isn't just missing — it's unsafe

A genuine multi-thread attempt against the shared model instance crashed with a CUDA device-side assert inside the pruning gather path. This is why batching needs a correctness fix first, not just more threads.

concurrent_profile_run_log.txt · 2,752 lines
768

KV-cache rebuilds every step

DynamicCache.from_legacy_cache() reconstructs the whole cache object every decode step, identically at both token counts — a generic tax, and the specific reason CUDA Graphs can't capture a stable buffer yet.

full_request_stage_breakdown.txt
2.3×

Prefill scales sub-linearly

~4.2× fewer tokens (587→139) should mean ~4.2× less prefill time. Measured: only 2.3× less. Some fixed, per-call cost doesn't shrink with the sequence — not yet root-caused.

What are we building?

Six engineering categories

Four were the original plan. Profiling evidence justified two more — neither is Triton, KV-cache, CUDA Graphs, or batching in disguise; each has a deliverable the other four can't produce.

T
core

Triton / Kernel Fusion

Fuses the diversity-selection loop and the gather/fixup path into single kernel launches.

  • Diversity-loop fusion — pruning-specific
  • Gather/fixup kernel — pruning-specific
K
core

KV-Cache Optimization

Replaces the per-step legacy-tuple rebuild with a persisted cache object, then a fixed-size buffer.

  • Persisted Cache object — pruning-enabling
  • Append speedup — prerequisite for CUDA Graphs
G
extension

CUDA Graphs

Captures the steady-state decode step to collapse 34k+ kernel launches per request into one replay.

  • Generic — helps both configs by a similar amount
  • Hard-blocked on KV-Cache
B
extension

Batching / Serving

Real tensor-level batched forward passes, replacing naive per-request serialization.

  • Serving optimization — capacity, not the 576-vs-128 delta
  • Hard-blocked on Serving Correctness
D
new core

Pruning Dataflow / Co-Design

Reordering, not kernel-writing: run the projector after the gather, investigate prefill's sub-linear scaling.

  • Zero new kernels — a code reorder with a correctness constraint on the anyres path
C
new prerequisite

Serving Correctness

Root-cause the concurrency crash. Produces no latency number of its own — its deliverable is "no longer crashes."

  • Unblocks Batching
  • Cheapest phase, done first

Problem

Shared model instance is not safe for concurrent access — a real crash, not a theoretical concern.

Evidence

indexSelectSmallIndex assertion, out-of-bounds index_select in the pruning gather path.

  3. Write a minimal two-thread repro isolating the exact race.

CUDA Graphs — decode-step capture/replay
Generic win: helps both configs by a similar absolute amount
extensionblocked on Phase 3▸
Problem

34,722 kernel launches in one 24-token request; decode CPU time exceeds CUDA time every step, both configs.

Design

Capture a single fixed-shape decode-step forward pass against Phase 3b's stable buffer; replay per step. EOS detection stays outside the captured region.

Success criterion

Decode ms/step drops at both configs by a similar absolute amount — a large 576-vs-128 relative shift would itself need explaining.

Rejection criterion

Any silent correctness break across a range of output lengths — validate exhaustively before trusting timing.

Difficulty / time

High · 6–9 days

Deliverable

Graph-capture implementation; before/after decode-ms/step, both configs.

5
Batching — basic, padded
Co-designed with Rithvik — csnbs/server.py is his file
extensionblocked on Phase 0▸
Problem

Throughput ceiling barely moves (2.166→2.249 rps) despite large per-request compute savings.

Design

Accumulate a small window of requests, pad + stack tensors, one batched forward pass, split outputs back per-request.

Implementation tasks
  1. Identify the batching boundary — a time window or fixed size with a max wait, chosen explicitly.
  2. Batched tensor construction: stack images, pad token sequences to the batch's longest.
  3. Support single-image batches first; multi-image is a further extension.
  4. Introduce prompt-length bucketing only if naive padding proves wasteful — measure first.
  5. Validate output separation — no cross-request contamination, including under different completion lengths.
  6. Benchmark batch sizes 1/2/4/8 explicitly.
Success criterion

Throughput ceiling measurably exceeds ~2.2rps at both configs.

Rejection criterion

Any cross-request output contamination is a blocking correctness bug, not a tradeoff.

Difficulty / time

Very high · 9–14 days

Deliverable

Batched request path; correctness suite; properly interleaved before/after load sweep.

How will we know each optimization worked?

The pruning-advantage formula

Applied to every phase that touches per-request latency. Distinguishes "made LLaVA faster" from "made more of VisPruner's own benefit appear as real latency."

VisPruner advantage before = (L576_before − L128_before) / L576_before
VisPruner advantage after  = (L576_after − L128_after) / L576_after
additional realized pruning gain = advantage_after − advantage_before

A pruning-enabling or generic fix (Phases 0, 3, 4) that improves both configs by a similar absolute amount will correctly show additional_realized_pruning_gain ≈ 0 — that's the expected, correct outcome, reported as "reduced total latency, did not change the realized pruning advantage," never oversold. Only Phases 1 and 2 are expected to show a clearly positive gain here; if they don't, that's a reportable finding, not a result to suppress.

When is the project finished?

Minimum vs. ideal completion

Minimum Complete project

  • Phase 0 completed and documented, whatever its outcome
  • Phase 1 (reorder) + Phase 2a (diversity-loop Triton) implemented, correctness-verified, benchmarked
  • Phase 3a (persisted Cache object) implemented and benchmarked
  • A final, properly interleaved load sweep
  • A final profiler-trace comparison against the original profiling-phase traces
  • All final-validation scripts reproducible, checked into scripts/
  • A written conclusion stating, plainly, how much of the 58%→13%→4% gap actually closed

Ideal Extended project

  • Everything in Minimum, plus:
  • Phase 2b (fixup kernel) implemented and benchmarked
  • Phase 3b (fixed-size buffer) implemented and benchmarked
  • Phase 4 (CUDA Graphs) implemented and benchmarked
  • Phase 5 (basic batching) implemented and benchmarked
  • The Optional bucket (paged KV, packed/varlen batching) revisited only if Phase 5's results create real memory pressure or measured padding waste to justify them
  • A comparison against vLLM's actual implementation of the toy versions built here

First implementation, two answers

Overall: Phase 0 — cheapest phase, de-risks Batching early, may inform Triton kernel safety.

First performance optimization specifically: Phase 2a, diversity-loop fusion — the strongest evidence of any candidate (56 measured iterations against a 56-iteration code prediction) and the clearest pruning-specific win available.

New categories, and why they earned their own section

Pruning Dataflow: zero kernel-writing — a reorder, not a Triton task.
Serving Correctness: produces no latency number — a prerequisite, not a form of Batching.
Forcing either into the original four would have hidden what each one actually delivers.
